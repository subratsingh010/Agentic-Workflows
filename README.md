# Employee Support AI Agent

Production-oriented open-source scaffold for a single Employee Support AI Agent serving policy Q&A, Jira time-log lookup, and leave application workflows.

## Stack

- Backend: Python, FastAPI, Pydantic, LangGraph/LangChain, SQLAlchemy, Alembic
- Data: PostgreSQL, Milvus, Redis, RabbitMQ
- Auth: Keycloak OIDC/JWT with backend-enforced RBAC/ABAC
- Async: Celery ingestion with retries and dead-letter routing
- Observability: OpenTelemetry, Phoenix, Prometheus, Grafana, Loki, Tempo
- Frontend: React, TypeScript, Vite, Tailwind
- Quality: pytest, integration/security/E2E tests, Ragas evaluation scaffold

## Architecture

The backend follows clean architecture boundaries:

- `domain`: typed contracts, entities, authorization and tool models
- `application`: use cases and ports independent of FastAPI, LangGraph, databases, and external APIs
- `adapters`: framework and infrastructure implementations
- `agent`: the single state graph orchestration
- `api`: HTTP routes and dependency wiring

The LLM never decides identity or permissions. The backend constructs `ActorContext` from a verified JWT and enforces authorization before enterprise retrieval or protected tool execution.

## Single Agent Workflow

The agent graph contains explicit nodes:

1. request validation
2. JWT authentication
3. ActorContext creation
4. RBAC/ABAC authorization
5. intent classification
6. missing-field detection
7. RAG retrieval
8. reranking
9. LLM generation
10. tool validation
11. confirmation guardrail
12. idempotency check
13. tool execution
14. audit logging
15. response

`thread_id` is used to persist and resume conversations/checkpoints in PostgreSQL.

## Full-Stack Mode

Docker Compose runs the backend in service-backed mode for everything except the intentionally mocked Jira and Leave clients:

```bash
PERSISTENCE_BACKEND=postgres
CACHE_BACKEND=redis
RAG_BACKEND=milvus
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://host.docker.internal:11434
OLLAMA_MODEL=qwen2.5:7b
```

In this mode conversations, checkpoints, and audit events are stored in PostgreSQL; idempotency and rate limits use Redis; policy retrieval seeds and queries a Milvus collection; policy answers are generated by Ollama from retrieved context. Jira and Leave remain typed mock clients.

## OpenAI LLM Mode

To use OpenAI instead of Ollama for policy answer generation, set:

```bash
LLM_PROVIDER=openai
OPENAI_MODEL=gpt-4o-mini
OPENAI_API_KEY=your_key_here
```

The app uses the OpenAI Python SDK with the Responses API. Intent routing, identity, authorization, confirmation, and tool execution remain deterministic backend logic.

## Local LLM with Ollama

The backend can use a local Ollama server for policy answer generation:

```bash
ollama serve
ollama pull llama3.1
```

Set these values in `.env`:

```bash
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=llama3.1
```

Intent routing, identity, permissions, confirmation, and tool authorization stay deterministic in the backend. Ollama only drafts the policy answer from retrieved policy context.

## Production RAG Retrieval

The RAG layer supports configurable dense, sparse BM25, and hybrid retrieval. In production Milvus mode, `MILVUS_NATIVE_HYBRID=true` stores both dense semantic vectors and Milvus-generated sparse BM25 vectors, then fuses results with Milvus `WeightedRanker` or `RRFRanker`. The in-memory backend keeps the same dense/sparse/fusion knobs for local tests without Docker. The reranker port supports score sorting and a deterministic heuristic cross-encoder-style reranker; a real open-source cross-encoder adapter can be added behind the same interface.

Important knobs:

```bash
RAG_RETRIEVAL_MODE=hybrid       # dense | sparse | hybrid
RAG_FUSION_STRATEGY=weighted    # weighted | rrf
RAG_DENSE_WEIGHT=0.6
RAG_SPARSE_WEIGHT=0.4
RAG_CANDIDATE_MULTIPLIER=4
RAG_RRF_K=60
RAG_BM25_K1=1.5
RAG_BM25_B=0.75
RAG_RERANKER_PROVIDER=score     # score | heuristic_cross_encoder
MILVUS_NATIVE_HYBRID=true       # Milvus-native dense + sparse BM25
```

Compare retrieval modes:

```bash
make eval-compare
```

## Policy Ingestion

Policy ingestion follows a source-to-index process. Markdown files live under `data/policies/source`, chunking is controlled by `RAG_CHUNK_SIZE` and `RAG_CHUNK_OVERLAP`, and `backend/scripts/build_policy_seed.py` writes both the top-level JSONL dataset and the backend-packaged seed used by Docker.

```bash
conda run -n agent python backend/scripts/build_policy_seed.py --chunk-size 120 --chunk-overlap 20
docker compose up -d --build
```

After changing chunking, run eval again from CLI or the UI. In production, the same chunking settings should be pinned per dataset version so retrieval scores are comparable across releases.

## Operations UI

The React console includes a Knowledge & Eval panel. It shows policy corpus size, eval case count, latest hit@K, document-hit, MRR, active RAG backend, and collection name. The panel can trigger packaged Goosle seed ingestion and run the policy retrieval eval through backend ops endpoints.

Ops endpoints are under `/api/v1/ops/*` and still require a bearer token. In local development the scaffold accepts `Bearer dev-token`.

## Security Controls

- OIDC/JWT verification using Keycloak JWKS
- Backend-enforced RBAC/ABAC before retrieval and tool calls
- Pydantic validation at API, agent, and tool boundaries
- Rate limiting, Redis-backed idempotency, locks, and caching hooks
- Structured redacted logs for secrets, JWTs, emails, and authorization headers
- Timeouts, retries, circuit breaker, and concurrency limiter wrappers for outbound clients
- Audit event persistence for protected actions

## Testing and Evaluation

The scaffold includes:

- unit tests for authorization, validation, idempotency, and tools
- integration tests for chat and resume semantics
- security tests for JWT/permission failures
- E2E API smoke tests
- policy RAG evaluation tests and a Ragas-ready JSONL dataset

Run backend tests:

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 conda run -n agent pytest -p pytest_asyncio.plugin -q backend/tests
```

Run the deterministic retrieval eval without calling an LLM:

```bash
conda run -n agent python backend/scripts/run_policy_eval.py --top-k 5
```

Use threshold gates for CI-style regression checks:

```bash
conda run -n agent python backend/scripts/run_policy_eval.py --top-k 5 --min-hit-at-k 0.70 --min-document-hit-at-k 0.80
```

When the stack is running, evaluate the full live API and its citations:

```bash
conda run -n agent python backend/scripts/run_policy_eval.py --live-api http://localhost:8000 --top-k 5
```

Live API mode also writes `outputs/evals/ragas_policy_eval.jsonl`, with `user_input`, `response`, `retrieved_contexts`, and `reference` fields for Ragas answer-quality scoring.

The synthetic Goosle policy corpus has 65 chunks and the eval set has 63 question cases across leave, Jira time logging, hybrid/remote work, expenses, security, devices, conduct, benefits, onboarding, payroll, privacy, and AI usage. Goosle is fictional sample company data, not real Google policy. Reports are written to `outputs/evals/policy_eval_report.json`. Retrieval metrics include MRR, Hit@K/Recall@K, Precision@K, nDCG@K, document-hit@K, and keyword coverage. Live API eval also records heuristic LLM-as-judge style answer metrics for correctness, groundedness, completeness, and relevance.

Some tests are marked and expect Docker Compose services.

## Tradeoffs

This repository includes replaceable mock Jira and Leave clients by design. Real integrations should implement the same ports and preserve backend-side authorization, idempotency, confirmation, and audit guarantees.


### Milvus-Native Hybrid Search

When `RAG_BACKEND=milvus` and `MILVUS_NATIVE_HYBRID=true`, the policy retriever uses Milvus for both retrieval routes: a dense `FLOAT_VECTOR` field for semantic search and a sparse `SPARSE_FLOAT_VECTOR` field generated by Milvus BM25 full-text search. Final candidate fusion is performed with Milvus `WeightedRanker` or `RRFRanker` using `RAG_FUSION_STRATEGY`.

The app still keeps the in-memory BM25 fallback so local tests can run without Docker, and `MILVUS_NATIVE_HYBRID=false` keeps the older compatibility path for Milvus setups that do not support BM25 functions.


### Production Embeddings

Dense retrieval uses Hugging Face SentenceTransformers. The default production-style setup is `EMBEDDING_PROVIDER=sentence_transformers` with `EMBEDDING_MODEL=BAAI/bge-small-en-v1.5` and `MILVUS_VECTOR_DIM=384`. Rebuild and ingest the Milvus collection after changing embedding model or dimension.
